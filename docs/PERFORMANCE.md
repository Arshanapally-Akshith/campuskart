# Performance — Phase 9

BUILD.md Phase 9 / ARCHITECTURE.md §12. Seeded 50k listings + 200k messages,
ran k6 (and, for chat, a documented non-k6 harness — see below) against the
API, measured, fixed what the numbers actually showed, re-measured.

**Deviation from ARCHITECTURE §12's wording**: "measured with k6 against the
deployed instance" assumes a live deployment, which doesn't exist yet
(that's Phase 10). Everything here was measured against a **local
production-mode build** (`NODE_ENV=production node dist/index.js`, single
process, no clustering) with real Docker Mongo 7 + Redis 7 — the same
correctness, not the same network/hardware a real deploy would have.

## Reproducing this

```bash
# 1. Seed 50k listings / 200k messages + mint k6 fixture JWTs
pnpm --filter @campuskart/api run seed:load

# 2. Build and run the API in production mode
pnpm --filter @campuskart/api run build
NODE_ENV=production node --env-file-if-exists=.env apps/api/dist/index.js
# add FEED_CACHE_DISABLED=true to the env to run the cache-off comparison

# 3. Index verification (drops the index, shows COLLSCAN, restores it)
pnpm --filter @campuskart/api run perf:explain

# 4. Feed cache hit-rate counters
pnpm --filter @campuskart/api run perf:cache-stats -- --reset   # before a run
pnpm --filter @campuskart/api run perf:cache-stats              # after a run

# 5. k6 scenarios (from repo root)
k6 run k6/scenarios/feedBrowse.js
k6 run k6/scenarios/listingDetail.js
k6 run k6/scenarios/reserveContention.js

# 6. Chat throughput (not k6 — see "Chat throughput" below)
pnpm --filter @campuskart/api run perf:remint   # tokens are 15min; re-run this before each scenario in a long session
pnpm --filter @campuskart/api run perf:chat
```

`k6/fixtures.json` (JWTs + listing/conversation ids, gitignored) is
generated by `seed:load` and read by every scenario script.

## 1. Index verification — the flagship before/after

Query under test (the browse feed's actual query, ARCHITECTURE.md §6):

```js
Listing.find({ status: 'ACTIVE' }).sort({ createdAt: -1, _id: -1 }).limit(21);
```

Collection: 50,000 listings, 44,019 `ACTIVE`.

| Scenario                                                   | Winning plan             | totalDocsExamined | totalKeysExamined |                                 executionTimeMillis |
| ---------------------------------------------------------- | ------------------------ | ----------------: | ----------------: | --------------------------------------------------: |
| **With** `{status,createdAt,_id}` index                    | `LIMIT → FETCH → IXSCAN` |                21 |                21 | 17ms (2–5ms on repeat runs, first-run page-in cost) |
| **Index dropped** (planner's own fallback)                 | `SORT → FETCH → IXSCAN`  |            44,019 |            44,019 |                                               284ms |
| **Index dropped**, forced COLLSCAN (`.hint({$natural:1})`) | `SORT → COLLSCAN`        |            50,000 |                 0 |                                                49ms |
| **Restored**                                               | `LIMIT → FETCH → IXSCAN` |                21 |                21 |                                                 2ms |

Reproduced with `pnpm --filter @campuskart/api run perf:explain`
(`apps/api/scripts/explainIndexCheck.ts` — drops the index, captures
`explain('executionStats')`, restores it in a `finally`, then re-verifies
the restored plan before exiting).

**The interesting part, found by measuring rather than assuming**: dropping
_only_ the named index does **not** produce a `COLLSCAN`. This collection
also has a `{status, category, priceInPaise, createdAt}` index (the
"filtered browse" index — `models/Listing.ts`) that shares the `status`
prefix. The planner picks that index instead, uses it to fetch every
`ACTIVE` document (it can't serve `category`/`price` filters that aren't in
this query, so it's an unfiltered walk of all 44,019 matches), and then has
to run a full in-memory `SORT` because that index's key order doesn't match
`{createdAt:-1,_id:-1}`. The plan still says `IXSCAN` — but it examines as
many documents as a collection scan would, and in this run was actually
**slower** (284ms) than a literal forced `COLLSCAN` (49ms), because it pays
index-traversal overhead _and_ the blocking sort, on top of a similarly
large document count. "An index is being used" is not the same claim as
"the _right_ index is being used" — a genuinely useful thing to have
measured rather than assumed, and worth having in your pocket for the
interview version of this question.

## 2. Feed cache hit rate (ARCHITECTURE.md §12 target: > 60%)

Counters added for this measurement (`lib/feedCache.ts`, Redis `INCR` on
every `getCachedFeedPage` hit/miss, read via `scripts/cacheStats.ts`) — see
[Instrumentation added](#instrumentation-added-not-behaviour-changes) below.

| Run                                                 |  Hits | Misses |  Hit rate |
| --------------------------------------------------- | ----: | -----: | --------: |
| Cache on, feed-browse scenario (100 VU, 40s)        | 4,744 |     88 | **98.2%** |
| Cache **off** (`FEED_CACHE_DISABLED=true`, control) |     0 |  4,657 |        0% |
| Cache on, after the fixes below (regression check)  | 4,626 |    123 |     97.4% |

98% is far above the 60% target — expected, given ARCHITECTURE.md §6's
design: only the first two pages are cacheable, 60s TTL, and a k6 "browse"
scenario naturally hammers page 1 the hardest (most real users load the
first page most often too). The 2–3% of misses are the version-bump churn
from the scenario's own writes during the run (report/reserve/etc. in other
scenarios bump `feed:version`, invalidating the cache) plus each unique
filter combination's first request.

## 3. k6 scenarios

All 40s runs at the VU counts below, run against the 50k/200k-message
dataset. "Before" = pre-Phase-9-fixes code; "after" = post-fixes (§5).

### Feed browse — 100 VU (ARCHITECTURE.md §12 target: p95 < 150ms)

|                                     |                          Before |                          After |
| ----------------------------------- | ------------------------------: | -----------------------------: |
| p95 (cache **on**)                  |                         11.86ms |                        10.36ms |
| p95 (cache **off**)                 |                         95.78ms |                    **15.62ms** |
| Data received (cache on, whole run) | 81 MB / 4,832 req ≈ 16.8 KB/req | 43 MB / 4,749 req ≈ 9.1 KB/req |
| Error rate                          |                              0% |                             0% |

Both cache-on numbers already met target before any code change — the
Redis cache was already doing its job. The **cache-off** number is the
honest measurement of raw per-request cost (DB query + serialization +
hydration), and that's where the fix (§5.1) shows: **6× faster**, and
payload size dropped **~46%**, because the feed was shipping every
listing's full `description` (up to 2000 chars) and `attributes` on every
row of every page, and the frontend feed view (`FeedPage.tsx`'s
`ListingCard`) never renders either field.

### Listing detail — 50 VU (target: p95 < 80ms)

|     | Before | After |
| --- | -----: | ----: |
| p95 | 9.23ms | 8.1ms |

Untouched this phase — no measured problem here to fix (single-document
fetch, already well under target), so nothing was changed. Reported as a
regression check, not a win.

### Reserve contention — 50 VU on 10 listings (target: p95 < 200ms)

Each of 50 VUs holds a stable identity for the run and immediately cancels
any reservation it wins, so contention is sustained for the full 40s
instead of the 10 listings being claimed once and then just 409ing forever.

|                                                  |                Before |                 After |
| ------------------------------------------------ | --------------------: | --------------------: |
| p95 (all attempts, win or lose)                  |               63.75ms |               17.95ms |
| Wins / attempts                                  | 3,100 / 8,255 (37.6%) | 4,810 / 9,460 (50.8%) |
| Correctness check (every response is 200 or 409) |                  100% |                  100% |

`reserveListing`/`cancelReservation` were **not modified** this phase — the
before/after gap here is ordinary run-to-run variance (background load,
JIT warm-up), not a code effect, and is reported as such rather than
claimed as a fix. Both runs meet target with a wide margin either way; this
scenario's real job (proving exactly one winner under concurrency) is what
`reservations.concurrency.spec.ts` already proves deterministically —
this k6 run is about latency under load, not correctness.

### Chat throughput (target: message round-trip p95 < 120ms)

**Deviation, and why**: chat delivery is Socket.IO (ARCHITECTURE.md §5),
and k6 has no built-in Socket.IO client — only raw WebSockets. Real
Socket.IO support needs the `xk6-socketio` extension, which means building
a custom k6 binary with the Go toolchain; **no Go toolchain is available in
this environment**. Rather than fake it with a bare-WebSocket script that
wouldn't actually speak the Engine.IO/Socket.IO framing the real app uses,
`apps/api/scripts/chatThroughput.ts` measures the same thing (concurrent
conversations, round-trip latency, p50/p95/p99, error rate) using
`socket.io-client` directly — the same client the frontend and the Phase 6
test suite use.

**First finding, before any latency measurement**: the first run (300ms
between sends, alternating two senders per conversation) came back with a
**51.6% error rate**. Not a bug — that cadence has each individual sender
emitting faster than one message per 2 seconds, which exceeds Phase 7's
**30 messages/minute/user** rate limit well within the 40s run. The rate
limiter, not raw server capacity, is the practical ceiling on how fast one
user can send — worth knowing on its own, separate from the latency number
below, which needed a send interval that stays under that limit (2500ms) to
measure infrastructure latency rather than abuse-prevention rejections.

| Concurrency                         | Before p95 | Before p99 | After p95 | After p99 |
| ----------------------------------- | ---------: | ---------: | --------: | --------: |
| 50 conversation pairs (100 sockets) |      174ms |      381ms | **148ms** | **266ms** |
| 10 conversation pairs (20 sockets)  |       97ms |      159ms |  **46ms** |  **69ms** |

The fix (§5.2 — the sender's own `markRead` call is no longer awaited
before the ack) measurably helped at both concurrency levels (roughly 2×
better at 10 pairs, ~15%/30% better at 50 pairs on p95/p99). Target is met
at 10-pair concurrency after the fix; **not fully met at 50-pair
concurrency** (148ms vs. 120ms target).

Honest caveat on that last number: `chatThroughput.ts` runs up to 100
concurrent `socket.io-client` connections in **one Node.js process** on
**one CPU thread** — a purpose-built load tool (k6, or Socket.IO's own
`socket.io-client` swarms run across multiple processes) would put less
scheduling pressure on the harness itself. The 10-pair vs. 50-pair gap here
is larger than the per-message server-side cost difference would predict,
which points at client-harness contention compounding the real server-side
number, not a claim that the server itself is fine at this concurrency —
just that this specific number has a disclosed measurement-tool ceiling
mixed into it, and a from-scratch k6-native harness (via `xk6-socketio`,
not available here) would be needed to fully separate the two.

## 4. Instrumentation added (not behaviour changes)

Two additions exist purely to make the required measurements possible —
neither changes production behaviour by default:

- **`lib/feedCache.ts`**: `feed:cache:hits` / `feed:cache:misses` Redis
  counters, incremented on every `getCachedFeedPage` call; read via
  `scripts/cacheStats.ts`. Also a `FEED_CACHE_DISABLED=true` env toggle
  (off unless explicitly set) so "cache on" vs. "cache off" is an actual
  A/B run against the same code, not two different builds.
- **`scripts/remintFixtureTokens.ts`**: access tokens are a real 15-minute
  TTL (`lib/jwt.ts`), correct for the app, but `k6/fixtures.json`'s tokens
  (minted once by `seed:load`) go stale partway through a multi-scenario
  testing session that runs longer than 15 minutes — this happened during
  this exact measurement run (the first reserve-contention attempt got a
  51% _401_ rate from expired tokens, not a real server problem — re-run
  after re-minting came back clean at 100% correct 200/409 responses). The
  script re-signs every fixture token in place from its own decoded
  payload, no DB round trip needed.

## 5. Fixes made, and why

### 5.1 `GET /api/listings` (browse + search): stop over-fetching

**Evidence**: 81 MB / 4,832 requests ≈ 16.8 KB average response in the
cache-on baseline run, and cache-**off** p95 was 95.78ms against an
already-generous 150ms target — most of both numbers is the query and
serialization cost of shipping every listing's full `description` (up to
2000 chars) and `attributes` on every row of every feed page.
`FeedPage.tsx`'s `ListingCard` renders `title`, `priceInPaise`, `category`,
`condition`, and a thumbnail — never `description` or `attributes` (that's
`ListingDetail.tsx`, a different endpoint, `GET /:id`).

**Fix**: `.select('-description -attributes')` + `.lean()` on both the
browse and search queries in `routes/listings.ts`, a new
`ListingSummary = Omit<Listing, 'description' | 'attributes'>` type
(`packages/shared/src/listings.ts`) that `FeedResponse.listings` now uses
instead of the full `Listing`, and a new `toListingSummary()` mapper
alongside the existing `toPublicListing()` (which `GET /:id` still uses,
unchanged, full shape). `.lean()` skips Mongoose document hydration
(change-tracking, getters, virtuals) across every row of every page —
free once `.select()` already means the mapper only reads plain fields
with no document instance methods.

**Result**: cache-off p95 95.78ms → 15.62ms (6×), payload ~46% smaller.
`GET /api/listings/:id` (single document, hydrated, already well under its
own 80ms target) was deliberately **not** touched — no measured problem
there, so nothing to fix.

### 5.2 Chat: stop blocking the ack on a non-critical write

**Evidence**: `chatThroughput.ts` at realistic (rate-limit-respecting)
concurrency showed p95 growing with the number of concurrent conversations,
and `sendMessage()` (`lib/chatService.ts`) had **three sequential** DB
round trips in the critical path per message: the seq-allocating
`Conversation.findOneAndUpdate`, the `Message.create` insert, then an
`await markRead(...)` that updates the _sender's own_ read pointer so their
own outgoing message doesn't inflate their own unread badge.

**Fix**: that third call no longer blocks the response. It's still
issued — the sender's unread count is still correct — just not awaited
before the ack goes out (`markMessageAsReadFireAndForget`, logs a warning
on failure instead of failing the send). Nothing about `sendMessage`'s
correctness contract changes: the client doesn't need the sender's own
read-pointer bookkeeping to have already landed before it can trust the
`{seq, id}` it got back.

**Result**: p95 46–148ms depending on concurrency (see table above), down
from 97–174ms before, at both concurrency levels tested. Re-ran
`conversations.spec.ts` (the unread-count assertions) and the chat spec
files 5× each afterward with zero flakes — the fire-and-forget window is
far smaller than the round trip time of whatever HTTP/socket call would
next check `unreadCount`.

### Considered, not done

- **`GET /api/listings/:id` `.lean()`**: same mapper, same argument as
  §5.1 applies in principle, but this endpoint was never a measured
  problem (single document, p95 already ~9ms against an 80ms target) — no
  evidence to act on, so left as a hydrated document rather than changed
  "for consistency" alone.
- **Denormalizing seller name/rating onto `Listing`** (the classic
  N+1-seller-lookup fix BUILD.md names as an example): this codebase
  doesn't actually do a per-listing seller lookup on the feed —
  `toPublicListing`/`toListingSummary` only ever return `sellerId` (a raw
  id string), never a hydrated seller name, so there's no N+1 here to fix.
  The one seller lookup in `routes/listings.ts` (`GET /:id`'s phone-number
  reveal) is a single extra query on a single-document endpoint, not a
  per-row cost in a list. Noted so it's clear this was checked, not missed.

## 6. Remaining bottlenecks / honest limitations

- **Chat throughput at 50-pair concurrency (148ms p95) still misses the
  120ms target**, with the harness-contention caveat above. The realistic
  next step, not done here, is a proper multi-process or k6-native
  (`xk6-socketio`) load generator so client-side scheduling stops being
  part of the number.
- **`cloudinary.ts` and the BullMQ queue-registration files
  (`cleanupQueue.ts`, `reservationSweepQueue.ts`) are outside this phase's
  scope** — they're I/O-bound external-service wrappers, not query
  performance, and Phase 3's docs already cover the no-live-Cloudinary-
  account constraint.
- **Text search** (`$text` relevance sort, offset-paginated, capped at 10
  pages) is the documented first thing to break at 100× scale
  (ARCHITECTURE.md §6/§14) — not re-litigated here since nothing in this
  phase's measurements changed that assessment; Atlas Search/OpenSearch
  remains the honest answer past this design's ceiling.
- This is all measured on **one local machine** running Mongo, Redis, the
  API, and the k6/Node load generators simultaneously — real numbers, but
  competing for the same CPU cores the server is trying to answer requests
  on. A real deployed instance (Phase 10) with the load generator on
  separate hardware would read differently, most likely better on the
  server side and worse for raw network-hop latency.
